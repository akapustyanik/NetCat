# Памятка по выпуску NetCat

Проверено 12 сентября 2026 года по GitHub Releases API репозитория [akapustyanik/NetCat](https://github.com/akapustyanik/NetCat/releases). Последний опубликованный релиз — **v0.4.0**, 30 июня 2026. Локальный коммит с названием v0.5.0 не является опубликованным релизом.

## Оформление

Сохранять стиль последнего релиза [v0.4.0](https://github.com/akapustyanik/NetCat/releases/tag/v0.4.0); дополнительные примеры — [v0.3.7](https://github.com/akapustyanik/NetCat/releases/tag/v0.3.7) и [v0.3.6](https://github.com/akapustyanik/NetCat/releases/tag/v0.3.6).

- Репозиторий исходников и релизов: `akapustyanik/NetCat`.
- Тег: `vX.Y.Z`.
- Название: `NetCat X.Y.Z`, как в 0.4.0. В 0.3.x встречалось `NetCat vX.Y.Z`.
- Описание на английском, с настоящими переводами строк, без декоративных секций, эмодзи и автоматической замены на GitHub-generated notes.
- Дата — фактическая дата выпуска, английское название месяца.
- В `Changes:` перечислять только реализованные и проверенные изменения.

```text
NetCat X.Y.Z

Updated Month D, YYYY.

Changes:
- Describe a completed user-visible change.
- Describe another completed change.
```

Не копировать буквальные `\n` из старых релизов 0.3.0 и 0.2.2: это дефект форматирования, а не образец.

## Файлы релиза

Сохранять существующую пару загружаемых файлов для Windows x64:

1. `NetCat-vX.Y.Z.zip`
2. `NetCat-vX.Y.Z.zip.sha256`

Автоматические архивы GitHub `Source code` не являются файлами приложения. ZIP должен быть полным self-contained пакетом с .NET runtime, необходимыми ядрами, зависимостями, лицензиями и `release-manifest.json`. В v0.3.7 прямо закреплена self-contained поставка; framework-dependent выпуск v0.3.4 отмечен как исключение, исправленное в последующих версиях.

Размер не является критерием готовности: текущий архив 0.4.0 — 177 428 602 байта, но будущий состав может отличаться. Проверять реальные файлы и запуск на системе без установленного .NET.

Для новых пакетов использовать однозначный формат SHA-256:

```text
<64 lowercase hex characters>  NetCat-vX.Y.Z.zip
```

Два пробела между хэшем и именем. Вычислять по окончательному ZIP. Не переносить примерные контрольные суммы из ТЗ.

ARM64 предусмотрен ТЗ, но в изученных релизах отдельного ARM64-архива нет. До добавления новой архитектуры проверить доступность всех ядер и драйверов; отдельно определить имя дополнительного архива, сохранив существующее имя x64 для совместимости обновлятора. Не выдавать x64-драйвер за ARM64-совместимый.

## Перед выпуском

Начиная с новой реализации, корень полного пакета: `NetCat.exe`, `modules/`, `metadata/`, `README.md`. EXE собирается self-contained single-file. Не выпускать архив из рабочей установленной папки: в нём не должно быть кешей, заданий обновления и резервных копий пользователя.

`metadata/release-manifest.json` (schema 1) содержит версию NetCat и девять компонентов. Каждый файл принадлежит одному компоненту и имеет SHA-256. Wintun, включая `modules/sing-box/wintun.dll`, принадлежит компоненту `wintun`; Python-среда Telegram принадлежит `tg-ws-proxy`. `metadata/installed.json` задаёт исходные версии. Новые версии пакета не должны уменьшать состав обязательных компонентов или менять владельца файла без миграции обновлятора.

Порядок: сборка → тест EXE → доверенная подпись `scripts/Sign-Release.ps1` → манифест `scripts/Write-PackageManifest.ps1 -RequireSignature` → ZIP `scripts/Pack-Portable.ps1` → SHA-256 ZIP → draft release. Упаковщик создаёт ZIP с путями через `/`. После любой правки EXE/модуля или переподписи пересоздать манифест и ZIP; не редактировать уже опубликованный asset.

`-TestBuild` отключает требование подписи только для локального тестового архива. Этот ключ не использовать в производственном выпуске. Сертификата подписи на текущем компьютере нет. Для GitHub-поставки нужен доверенный сертификат/сервис подписи с постоянным ключом издателя; самоподписанный сертификат не устраняет SmartScreen. Доверенная подпись тоже не гарантирует отсутствие предупреждения до накопления репутации — [Microsoft](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).

Перед публикацией проверить сценарий «старый NetCat + модуль новее архива + закреплённый модуль»: должна обновиться программа, а оба модуля остаться прежними. Установка должна отменяться при неверной SHA-256, неполном манифесте, чужом пути или недоверенной подписи текущего или следующего EXE NetCat. Сохранение профилей проверить отдельно: пользовательский `%LOCALAPPDATA%/NetCat` никогда не включается в архив и не перезаписывается из него.

- Сверить версию сборки, манифеста, тега и release notes; проверить существующие теги и релизы, не перезаписывать опубликованные версии.
- Собрать Release и выполнить тесты парсеров, конфигураций, обновления/отката и восстановления сетевых настроек.
- Проверить ZIP, SHA-256, комплектность, запуск без отдельно установленного .NET и работу выбранных ядер.
- Проверить обновление со старой версии: сохранение профилей, правил, настроек, закреплённых и отдельно обновлённых модулей.
- Убедиться, что в пакет не попали пользовательские подписки, ключи, токены, реальные профили, логи и локальные настройки разработчика.
- Зафиксировать для каждого модуля источник, версию, архитектуру и проверенную контрольную сумму; включить требуемые лицензии.
- Выпуск должен ссылаться на точный проверенный коммит. Пушить только предназначенные для этого коммиты и конкретный тег.
- Сначала создать draft с полным описанием и файлами, проверить результат, затем опубликовать в рамках порученного выпуска.

Пример команды **после появления проверенной сборки и уже отправленного тега** (X.Y.Z заменить):

```powershell
gh release create vX.Y.Z `
  artifacts/NetCat-vX.Y.Z.zip `
  artifacts/NetCat-vX.Y.Z.zip.sha256 `
  --repo akapustyanik/NetCat `
  --verify-tag `
  --title "NetCat X.Y.Z" `
  --notes-file docs/releases/vX.Y.Z.md `
  --draft
```

Передавать описание через файл, сохраняя переводы строк. Публикация выполняется отдельно от создания локального тестового билда.

## Геоданные в новых пакетах

Начиная с тестового билда 09 полный манифест включает также `geoip` и `geosite` (итого 9 компонентов), каждый в собственной папке `modules/<key>`. Перед сборкой выполняется `scripts/Fetch-Geodata.ps1`. Базы — отдельный набор данных проекта Loyalsoldier, не часть официального ядра Xray. Не удаляйте файлы LICENSE и SOURCE из комплекта.

Версии баз имеют формат даты `yyyyMMddHHmm`; обновляющий код должен поддерживать их сравнение. Помощник обновления ранних тестовых билдов, ожидающий ровно семь компонентов, не примет такой пакет: для перехода с них на 09 нужно запустить EXE из новой папки. Это ограничение учитывайте перед первым публичным релизом новой реализации.

Самообновление из неподписанного EXE запрещено начиная с билда 10. Помощник принимает одноразовый IPC-канал текущего процесса; JSON-путь в командной строке больше не поддерживается. Новые пакеты не должны содержать prepared.json или пользовательские задания. Перед выпуском требуется проверка полного цикла на двух доверенно подписанных EXE. Архитектурный переход от административного UI к отдельному привилегированному сервису остаётся открытой работой.
