# NetCat: исходные решения

Дата: 2026-09-12. Основание: `ТЗ.txt` и указания пользователя. Пользователь подтвердил создание заново, без восстановления старой реализации из Git. Выбран вариант **Focus**: спокойный интерфейс с верхней навигацией и простым главным экраном. Подробные настройки находятся на специализированных страницах. Скриншоты пользователя — функциональные ориентиры, их оформление не копировать. Дополнительные требования и критерии приёмки: `docs/FOCUS_SPEC.md`.

## Платформа и состав

Windows 10/11, C# 12, .NET 8, WPF, CommunityToolkit.Mvvm. Интерфейс приложения нативный, без Electron/CEF/WebView2. Визуальные макеты для выбора дизайна не входят в исполняемое приложение.

Слои: NetCat.Core, NetCat.Engine, NetCat.Network, NetCat.Updater, NetCat.UI. Основные функции: профили и подписки, VPN/TUN, маршрутизация по приложениям/доменам/IP, независимые Zapret и Telegram WS proxy, резервный узел, диагностика, график трафика, редактор JSON, трей, автозапуск, темы, модульные обновления и откат.

Указание пользователя про Flowseal имеет приоритет над примером `bol-van/zapret-win-bundle` в ТЗ. Не подменять Flowseal другим форком. У tg-ws-proxy есть отдельные Windows x64 и ARM64 assets; фактические имена проверять при реализации. Telegram WS proxy — локальный MTProto→WebSocket модуль, не обычный SOCKS-сервер. Не путать его с SOCKS inbound sing-box.

Не выбирать произвольный asset по первому совпадению. Проверять архитектуру, тип пакета, стабильность релиза, совместимость конфигурации, происхождение и контрольную сумму. Локально вычисленный хэш сам по себе не подтверждает подлинность: нужен доверенный ожидаемый digest/подпись либо проверенный зафиксированный манифест. При отсутствии такого основания не сообщать пользователю «проверено».

Обновлять компоненты независимо: staging → проверка → остановка нужного процесса → резервная копия всего комплекта → замена → проверка запуска → откат при ошибке. `pinned` запрещает обновление. Обновление оболочки сохраняет пользовательские данные, pinned и более новые отдельно установленные модули. Для Zapret учитывать bin, DLL/SYS, стратегии и списки вместе.

## Уточнения к ТЗ для реализации

1. **Failover.** В [документации URLTest](https://sing-box.sagernet.org/configuration/outbound/urltest/) описан выбор outbound по проверкам и поведение существующих соединений. Это не обещание параллельных SYN для каждого потока и переноса любого существующего TCP-сеанса на другой сервер. Первым реализовать измеряемый hot standby и переключение новых соединений; бесшовность и racing требуют отдельного прототипа и проверки. Не заявлять нулевую задержку и отсутствие разрывов без доказательств.
2. **Версии конфигураций.** JSON из ТЗ содержит устаревшие DNS/TUN/route поля; см. [deprecated](https://sing-box.sagernet.org/deprecated/). Генерировать конфигурацию для закреплённой совместимой версии, прогонять `sing-box check` перед запуском и обновлением ядра.
3. **OpenVPN.** Нарисованный в ТЗ SOCKS bridge требует отдельной реализации: обычный OpenVPN CLI не создаёт такой сервер сам. Определить маршруты/адаптер и способ соединения с главным маршрутизатором, исключить петли.
4. **AOT.** Не приравнивать AOT-совместимые архитектурные решения к готовой Native AOT сборке всего WPF приложения. Базовая поставка — self-contained; совместимость выбранного стека с AOT проверять отдельно по [Microsoft](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/).
5. **ARM64.** Проверить все драйверы и модули на целевой архитектуре; эмуляция пользовательского x64 процесса не решает совместимость kernel-драйвера.
6. **Завершение.** ProcessExit недостаточно для восстановления после аварии/отключения питания. Нужны журнал внесённых изменений, управление дочерними процессами и восстановление при следующем старте; очищать только ресурсы NetCat.

## Этапы после выбора интерфейса

1. Утвердить направление и основные экраны, собрать нативный WPF каркас с тестовыми состояниями.
2. Модели, хранилище, импорт профилей, управление процессами, первый работающий sing-box VPN/TUN.
3. Маршрутизация/DNS, Xray/OpenVPN, независимые Flowseal-модули, реальные метрики и резервирование.
4. Обновления и откат, восстановление сети, трей/автозапуск, проверка на целевых Windows и архитектурах.
5. Полная сборка, упаковка и публикация по `RELEASE_GUIDE.md`.

Текущий результат — подготовка проекта и выбор интерфейса. Исполняемая сборка не создана и новый релиз не опубликован.
